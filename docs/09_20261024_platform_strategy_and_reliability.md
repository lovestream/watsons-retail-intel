# 09｜2026-10-24 平台选型、API 自主化、Muse 协同与稳定运行改造方案

> 状态：**方案已归档，尚未实施**（设计/验收基线，不代表线上已切换）。
> 目标读者：项目维护者、Codex/QwenPaw/Muse 执行代理、经营情报使用者。
> 范围：仅中国大陆「即时零售 × 个护美妆」公开情报，服务屈臣氏线上零售经营判断；沿用**日报停发、每日积累事件池、周/月/年报+音频+邮件**的产品决策。
> 依据：2026-10-24 读取的仓库 main 分支源码/配置、`docs/01~08`、`AUDIT_20260811_collection.md`；产品能力以当日官方文档为限。仓库中旧日志不能代替当前线上运行证据。

## 0. 执行结论

**建议主线：保留现有 Python 情报管线和 QwenPaw 操作入口，改为独立确定性调度 + 自有合规 API Key + 模型适配层；引入 Muse 做辅助研究、差异化选题和人工复核，不直接接管生产调度、历史账本和最终邮件投递。**

不赞成两种极端：
1. 继续完全依赖 QwenPaw 的 *agent 型 cron → LLM 推理 → 运行脚本*；一旦 agent 的模型服务失效，脚本可能根本未启动。
2. 把仓库提示词交给 Muse、完全放弃原有数据采集/去重/覆盖率/送达账本，以「它会自动搜索」代替可验证的业务流程。

目标架构（**目标态，不是当前实现**）：

```text
GitHub（代码、策略、提示词、测试、变更审计；不保存密钥）
    │ 受控发布
    ▼
NAS/固定运行环境（独立调度器 systemd timer / cron / 受控 Actions，三选一）
    │  不经过 LLM 才能启动，单一调度权威
    ├─ 每日事件池：来源发现 → 网页获取 → 发布/事实日期核实 → 清洗
    │               → 去重/聚类 → 重要度评分 → 商业分析 → 事件事实库
    ├─ 周/月/年报：覆盖度门禁 → 证据包 → 生成 → 审校 → HTML/播客
    │                                                  │
    │                                               发送账本 → 邮件
    ├─ API Gateway/Adapter：自有主模型 Key + 异厂商备用（预算、限流、审计）
    └─ 监控：心跳 + 最近成功日 + 质量漏斗 + 漏报/迟报 + 告警 + 手工补跑
                           ▲                  │
                           └── Muse 辅助专题研究/补漏候选（受控 JSON）
                                → 来源校验 → 原管线入池或人工复核
QwenPaw：运维对话、手工触发、状态询问、Skills/MCP 界面（不作为唯一启动条件）
```

### 方案取舍

| 维度 | A：原 QwenPaw + 自有 Key（原样维持调度） | B：完全迁至 Muse | C：推荐混合架构 |
|---|---|---|---|
| 现有规则、历史事件账本复用 | 高 | 需重新实现/迁移 | 高 |
| 稳定定时、可追溯执行 | **不足**：若仍靠 agent 型 cron 则无根治 | 需单独验证定时、持久化、重试和审计能力 | 独立确定性调度负责 |
| 自主搜索及开放题研究 | 已有搜集工具，深度探索需加强 | 较强，适合开放研究 | Muse 补强高价值缺口 |
| 可控成本和模型切换 | Key 接入后可改善，但脚本模型硬编码需处理 | 平台定价、配额、集成权限须核验 | 关键模型可选、按层配额 |
| 可复现的证据链与回归测试 | 高 | 需要自行补足 | 高 |
| 建议 | 作为过渡，不宜终态 | 只做 PoC，不应整套替换 | **主方案** |

注意：「自有 API Key」不等于「免费」或「自动稳定」；可用性取决于服务商 SLA、余额/额度、调用峰值、模型兼容性、网络和代码熔断设计。

## 2. 路线 A：在 QwenPaw 接入自有 API Key（推荐保留，但需两层改造）

### 2.1 两个互不自动同步的调用层

1. **QwenPaw Agent 层**：官方支持在 Console → Settings → Models 配置 Provider 的 API Key；亦支持 custom base URL/provider，并提供 Skills、MCP、Cron。该配置用于 QwenPaw 自身智能体调用。
2. **本项目 Python Pipeline 层**：`skills/utils/llm_client.py` 有自己的一套 Provider 选择、Key 加载、重试和 API 协议。**在 QwenPaw 控制台填入 Key，不代表本项目脚本自动改用新模型！**必须单独做适配器/配置迁移并验证每项业务技能。

官方参考：
- QwenPaw 快速上手：https://qwenpaw.agentscope.io/docs/quickstart/
- QwenPaw 模型配置：https://qwenpaw.agentscope.io/docs/config/
- QwenPaw 定时任务/CLI：https://github.com/agentscope-ai/QwenPaw/blob/main/website/public/docs/cli.en.md

### 2.2 建议技术实现（拟议配置，禁止当作已存在）

- 新建与供应商解耦的 `LLMProvider` 适配接口：`chat(messages, response_format, max_output_tokens, timeout, request_id)`，统一文本/JSON 解析、错误分类、usage 与计费统计。须验证具体模型 API 的实际兼容性，不能简单替换 `base_url`。
- 将「任务能力」映射到独立可配置的模型策略，而非所有任务强制一个模型：
  - 标题与轻量预筛：规则优先，低价模型用于不确定文本；
  - 事件抽取、归类：性价比模型，严格 JSON schema 校验；
  - P0/P1 商业影响分析及周期报告：高质量主模型；
  - 最终审稿/事实反查：尽量使用与生成层独立的模型/规则组合。
- 主/备模型至少跨 Provider，且分别执行周期性真实探针。**备用仅在批准的预算内启用**；不能因为主模型失败无限追补或悄悄切贵价模型。
- 在 `config/model_router.yaml` 里只存 `provider_id`、`model_id`、质量/价格级别和引用的环境变量**名字**；具体密钥来自容器 Secret/权限受限的环境文件或 secret manager，不写 GitHub。
- 为每类报告配置单任务最大花费、调用次数、Token 上限和最大并发；设置每日/每月硬预算，超限标记 `budget_exhausted` 并禁止发送未经审校的降级报告。
- 对 401/403（鉴权/权限）、402/余额、429/限速、5xx/超时、格式校验失败采用**不同**恢复策略；429 尊重 Retry-After，重试指数退避+随机抖动；引入熔断，失败不得无上限重试。
- 生产运行时禁止记录完整 API Key、Cookie、私有源正文及敏感 Headers；日志仅记录 Provider 名称/请求 ID/成本/耗时/脱敏错误分类。
- 不再依赖 keyless、浏览器 UA 模拟和未经确认的免费聚合入口作为关键业务的稳定性承诺。删除旧兼容逻辑须单独 PR 和回归测试，不在文档修改中执行。
- 发布采取 shadow 比对（相同冻结证据包比较两模型输出）→ 少量灰度 → 生产切换 → 旧路由可回滚；测定真实成本后才设定具体金额。

### 2.3 「自有 Key」操作规程

1. 选择有正规 API 文档、配额和账单的供应商；确认访问区域和合规性。
2. 创建**项目专用、最小权限** Key，限制额度与周期预算；不同环境/用途分离。
3. 分别配置 QwenPaw 运行层与 Python 服务层的 Secret；进行只读探针与 1 条结构化事件调用，不能把 Key 放到日志、PR、Issue、Muse 聊天或者仓库。
4. 使用 14 天实际日志比较可用率、单事件成本、JSON 有效率和审稿通过率；预算与性能过门才切换。
5. 完成切换后撤销无用凭证并记录旋转日期。任何历史泄漏需立即旋转，不能只靠 `.gitignore`。

## 3. 路线 B：Muse 辅助研究方案（仅先做 PoC）

Muse 官方产品页面宣称支持浏览网页、连接应用、持续后台监测与多步骤任务，但**不能据此推导出**已具备可调用的 GitHub 原生读写 API、企业级准时交付 SLA、稳定的批处理 API、长久运行环境或完整外部账本事务语义。各项能力须在用户当前账号实际测试。

官方参考：https://ai.meta.com/muse/

**建议 Muse 的工作范围：**
- 对指定主题做深入研究：美团闪购/京东秒送/淘宝闪购/抖音小时达的个护美妆策略；丝芙兰、万宁等竞品的新动作；平台招商、佣金、流量与履约政策；类目和场景机会。
- 对已有事件池做 **差异搜索**：近 7/30 天高价值新增事实、独立佐证、遗漏重要政策/活动/品牌动作；可输出新候选，不直接判定真伪。
- 对周报提出「哪些判断还缺反例／竞争对手视角／执行成本与可验证 KPI」；不直接覆盖最终生产稿、发送邮件或改写去重账本。
- 输入优先采用 GitHub 中**公开可分享的规则说明 + 脱敏精选事件包**；如果 Muse 可以读取指定仓库再授权只读。无持久 GitHub 连接时，导入版本化 Markdown/PDF 规则，不依赖一次聊天自然记住所有规则。
- 输出强制结构化为候选：`candidate_id / topic / claim / evidence_urls[] / published_at / event_at / region / channel / competitor / business_hypothesis / uncertainty / collected_at`；**未经来源验证只能放候选池**，不得直接写入权威事件池。
- 原系统做 URL 可达性、发布日期和事实日期分离、内地主体、品类相关性、URL/事件指纹去重、引用真实性核验；无法验证则标 `needs_review`。
- Muse 不保管 SMTP、GitHub 写 Token 或生产 API Key，不赋予默认自动发信/删改数据权限；安全沙箱和最小权限应单独验证。

**四周对照试验（不改生产报送）：**
- 第 1 周：冻结 10~20 个典型研究问题和 2~4 周历史事件包，制定统一评分尺。
- 第 2~3 周：Muse 与现有搜索链路并行，记录新增**被独立验证**的高价值事实、误报、重复、投入时间、可溯源率和总成本。
- 第 4 周：以盲审方式评估对实际经营问题的贡献。只有当 Muse 的净增价值明显，且不存在无法接受的合规/稳定风险，才把 Muse 候选接到正式管线前的受控输入口。
- 若 Muse 无可靠自动推送接口：仅保留专题研究/人工补漏；**不设计依赖它定时调用的生产链路**。

## 4. 产品逻辑升级：从「文章收集」升级为「经营信号与决策」

### 4.1 情报层级（防止素材很多、决策很少）

- L0 原始素材：文章 URL、标题、抓取时间、来源、页面快照/hash。
- L1 可核查事实：主体、具体动作、发生时间、原始出处及独立佐证（禁止直接复述营销宣传为确定事实）。
- L2 经营信号：跨来源合并后，可区分平台政策、竞对动作、品类趋势、履约/价格/获客变化；每一条关联原始证据。
- L3 经营判断：证据→可能机制→对屈臣氏的影响→适用范围与不确定性。
- L4 行动建议：责任渠道/执行动作/优先级/观察 KPI/验证窗口/风险与反证条件。不得假设已获得企业内部经营数据。

从 L0 到 L4，每层必须可逆向追溯；没有 L1 的事实，不得包装成 L3/L4 的确定判断。

### 4.2 保留和加强的硬边界

- 仅大陆主体及大陆经营相关内容；**核心交集**必须与「即时零售 × 个护美妆」相关，不能因仅出现「零售」「美妆」「京东」泛词就入池。
- 分开存储 `published_at`（文章发表）、`event_at`（事件发生）、`first_seen_at`（系统发现），以防旧闻二次分发变「今天新发生」。
- 来源分级：平台/企业原公告优先，可信媒体次之，聚合转载仅作线索；数据必须记录统计口径，促销力度/GMV 等只能在有明确信源时使用。
- 去重是 **URL → 同事实多稿 → 同主题跨天变化** 三层；既不能重复，也不能错杀新进展。
- 值得报告的重点：平台渠道政策/流量与履约变化、竞争对手策略、品类需求和商品结构变化、品牌/新品/场景、价格促销及毛利影响、风险与机会。排除投资股价/财报/IPO、境外主体、无经营意义广告。
- 对周/月/年报建立「新增信号、延续趋势、反转迹象」的区别；绝不把报道数量当销量增长或因果证据。
- 输出从「本期十条新闻」转为「本期 3~5 个经营判断 + 证据 + 备选解释 + 可执行动作」，但证据不足必须明确「暂无可信新增信号」。
- 建议对屈臣氏三类线上渠道群分别解释影响与差异，避免空泛的「加强合作、关注趋势」；只对公开证据可支持的内容给结论。

### 4.3 来源优化与成本节流

- 以**高价值、去重后、可引用的 L2 信号数 / 千次请求与每元成本**，而不是抓取条数评价来源。
- 每周自动统计来源：成功率、超时、验证码/反爬、有效正文、入池率、L2 贡献、人工判真率、成本、独有事件数。
- 连续失败源先熔断/降低频次并报警，不能永久自动删除高价值来源；恢复需探针验证。尊重 robots.txt、平台条款、反爬和数据访问限制。
- Search API 主要负责发现 URL，确定性爬取/官方来源补全正文；Muse 负责深度专题或遗漏候选，避免三套工具无差别重复全量采集。
- 针对旧审计 TopHub/XCrawl/Tavily、关键词 `711` 等问题**先核实当前代码及实时产出**，再决定修复/禁用；不得照抄 2026-08 结论。
- 将筛选优先级从「全部送 LLM」改为：硬规则过滤 → 高价值/疑难段 LLM → 证据校验 → P0/P1 深度分析。
- 增加人工标注黄金样本：真正重要 30 条、无关 30 条、时间误导 20 条、重复 20 条、虚假/单一来源 20 条；每次变更跑召回、误报、时效与事实回归。

## 5. 稳定运行的设计与验收标准

以下是**拟议 SLO，需先建立现状基线**，不是已经达标。

| 能力 | 建议门槛 / 最小验收证据 |
|---|---|
| 调度启动 | 连续 30 天计划任务启动率 ≥99%；以系统级执行记录为准，不能用 agent 「已启动」回复作证 |
| 每日事件池 | 30 天成功形成**有效完整事件池**比例 ≥97%；0 条信号可合法成功，但字段/窗口/来源检查必须通过 |
| 周/月/年报交付 | 目标窗口内成功或明确受控拒发 ≥95%；**漏报不得静默**，失败留可定位 manifest |
| 引用与事实 | P0 关键判断 100% 有可核查证据链接；按盲审抽样衡量发布日、事实日、引用链接有效率 |
| 幂等 | 同 `report_type + period_id + version + recipient` 成功发送次数不超过 1；失败重试安全 |
| 成本 | 月预算硬上限不可突破；记录每步 token、调用数、费用、源请求次数；异常涨幅告警 |
| 恢复 | 模拟网络断开、主 API 故障、重启、重复触发、缺失某一天事件池，均可定位、可人工补跑 |
| 安全 | 仓库/日志/报告无有效 Key 或 Cookie；所有敏感凭证独立授权、可轮换、可审计 |

**五条不可妥协的可靠性原则：**

1. **启动无模型依赖**：固定主机调度器启动 Python，QwenPaw 只作交互控制层。仅能运行 QwenPaw agent cron 的环境视为过渡环境；升级为能运行 Linux cron/systemd timer/NAS Task Scheduler 的执行器，或独立 GitHub Actions（注意长期浏览器、网络与密钥限制）。
2. **一个调度权威**：每天事件池只允许一处定时触发，报表亦然；迁移时先停旧的两条 agent cron，核对新旧不会同时发送。建议每日 07:15 后采集昨 07:00~今 07:00 的闭合窗口，周期 09:00 后执行前必须验证日事件池已完结；实际时刻需按采集耗时调优。
3. **完成信号可验证**：shell 退出码 + `run_manifest` + 关键输出 schema/hash + 原因分类；启动成功不等于完成成功，文件存在不等于数据有效。当前 `--continue-on-error true` 需检查关键步骤失败是否被错误当作成功；有问题必须修复退出码传播。
4. **先落盘，再发布**：每一步原子写临时文件→校验→rename，标识 `pending/running/succeeded/degraded/failed/published`；周期覆盖率不足时不伪造正常报告。对有意缺口、临时降级、未审核稿按状态区分。
5. **实际送达事务化**：持久化的发送台账必须原子检查/占位、唯一键防并发；SMTP 发送结果不确定时标 `unknown` 并走核对流程，**不得自动盲重发**。有明确收件人和授权的报告才可投递。

### 故障与告警矩阵

| 事件 | 自动动作 | 告警 |
|---|---|---|
| 主模型 429/5xx/暂时超时 | 限额重试、熔断、预算内备用，保留任务状态 | 达阈值才汇总警告 |
| 主备模型均不可用 | 保存已校验事件池/规则摘要，周期正式稿 `sendable=false`，不可静默发低质替代 | **单条关键告警** |
| 某个补充资讯源失败 | 标注来源降级，继续已有可信渠道 | 非关键汇总，不刷屏 |
| 关键来源全挂或覆盖度不达标 | fail-closed，启动有限补搜；仍不达标阻断正式报送 | 关键告警 |
| 时间错位、日期验证失败 | 停止错误历史报道入最新池，保存待复核 | 按比例阈值报警 |
| 邮件接口失败/超时 | 确认台账与远端送达状态后重试；避免重复发送 | 投递失败告警 |
| 调度器没启动/主机断线 | 独立 watchdog 检测「上次成功时间」；恢复后有限补跑 | 立即发送**单次去重**告警 |
| Muse 无响应或研究未完成 | 跳过可选 Muse 候选，核心任务继续 | 不影响周期交付 |

### 运行与恢复 Runbook（需实现与验证）

- 启动：系统级调度器用受控服务账户、固定 Python 虚拟环境/锁定依赖运行，进程超时与并发锁可监测；避免生产时缺什么就自动 `pip install` 拉最新版引入供应链和不确定性。
- 自检：记录 `last_scheduler_tick`、`last_daily_success`、`last_periodic_success`、`last_delivery_success`、`next_run`、Key 剩余额度（如 API 提供）、磁盘剩余、网络/来源健康。
- 补跑：指定 `--date` / 周期 `period_id`，从失败的步骤恢复并验证依赖；在正式启用前检查 `scripts/run_periodic.sh` 的日期参数**当前没有传给 Python CLI**的限制，修好后才能保证周期定点补跑。
- 账本：原始文章 hash、事件指纹、运行 manifest、发送幂等键必须放持久化存储，备份有恢复演练；不能因清缓存或切平台丢历史重复判定。
- 部署：预发布→测试样本→dry-run（**禁发邮件**）→影子运行→灰度→切换；每次变更生成版本号、配置 hash 和可回滚指针。
- 观测：技术健康与业务价值拆开；周/月输出一份很短的健康摘要，写明「计划/成功/失败/恢复、费用、事件数、有效来源占比、重大发现、未解决风险」。
- 数据安全：如仓库继续公开，代码与数据必须经脱敏/版权及业务机密审查；历史中的 Cookie、凭证、邮件/日志若已暴露应先轮换再清理追溯，不能仅删除当前文件宣称解决。
