# 10｜Muse 网页端独立建设方案：以 GitHub 为共享项目入口

> 2026-10-24。**本文件修正第 09 篇中对 Muse 集成方式的设计**：Muse 版不作为原 QwenPaw 程序的在线插件，也不借用本地 Agent 的模型、调度或密钥；而是在 Meta Muse 网页端**独立实现另一套业务等价的经营情报工作流**。
>
> **交给 Muse 执行的完整任务书：[muse/MASTER_GOAL.md](../muse/MASTER_GOAL.md)**。本文件解释架构选择，不重复任务书。

## 1. 为何修订方案

原 09 文档的混合架构包含「Muse 搜索到候选 → 原 Python 管线自动导入」，却没有确定的 Muse 网页端到本地 Agent 的双向通信机制；不应把此链路当作已能部署的方案。

已发现：
- Muse 官网明确介绍其 **Secure VM 专用浏览器、App Connectors、后台任务与监测**；但实际账号下的 GitHub 权限、存储、定时和投递必须测试，不能借产品介绍直接断言部署完成。官方： https://ai.meta.com/muse/
- GitHub 上存在 **Meta Muse AI 官方 GitHub App**，页面写明通过 **GitHub 官方 MCP server** 让 Muse 用户连接账号并访问 repositories、issues 和 pull requests，操作遵守连接用户身份和 Muse 审批控制： https://github.com/apps/meta-muse-ai 。这意味着**GitHub 是可操作的实际共享入口（仍需当前账号授权与实测）**。
- Muse 网页 Agent、Muse Code（命令行编程 Agent）和 Meta Model API 是三种不同的使用方式。本轮针对**网页 Muse**，不能把后两者的开发功能等同为网页账号自带能力。Meta 开发文档： https://dev.meta.ai/docs/overview

## 2. 目标结构

```text
                           GitHub: lovestream/watsons-retail-intel
                 公共项目规则/docs/config + Muse 独立任务书 muse/*
                      ▲                                  ▲
                      │                                  │ GitHub Connector / MCP
                 QwenPaw 本地                         Muse 网页 Secure VM
               既有 Python 情报管线                     Web 发现/检索/验证/分析
                独立运行与投递                          独立记忆/报告/监测
                      │                                  │
                QwenPaw 版成果                       Muse 版成果（优先内部持久化）
                      └───────── 不强制互相调用 ──────────┘
                              对照检查事实质量与经营价值
```

| 能力 | QwenPaw 旧版 | Muse 新版 |
|---|---|---|
| 执行环境 | 现有本地 Agent + Python 脚本、自己配置 API | Muse 网页端的授权 Agent/浏览器 |
| 搜索 | 脚本爬取/RSS/API/浏览器 | Muse 自主网页研究、已授权连接器 |
| 规则 | 现有 docs/config | 先提炼原规则，在 `muse/` 形成可复用说明 |
| 历史 | 本地事件/来源/送达账本 | 新建 Muse 版历史、可验证持久化机制 |
| 报表 | 既有周/月/年 HTML+播客 | 先文字版与事实审校，逐步验证音频/邮件 |
| 定时 | 原 QwenPaw 任务（存在已知可靠性问题） | 仅当当前账号支持且通过真实运行测试才启用 |
| 集成 | 无需 Muse 控制 | **GitHub 共享规则与经过授权的成果**；非 API 双向控制 |
| 数据写入 | 保持不变 | 仅独立 `muse/` 或独立私有存储 |

## 3. 为什么先独立建设，而非先混合联动

1. 两个环境的登录、密钥、定时机制各自独立，强行直连要新增桥接服务器、轮询接口和失败恢复，维护成本高；独立可更快检验 Muse 实际能力。
2. 不会因为 Muse 一次搜索失败导致原系统停摆，也不会因为 QwenPaw 模型或调度故障阻断 Muse 工作。
3. 业务规则可复用，实时报表则独立生成，更容易判断 Muse 自主搜索到底带来增益，避免把原系统已有新闻当 Muse 新发现。
4. 以后如果需要「两个系统信息互通」，可以基于 GitHub 规范化的事件摘要文件或 PR 实现**异步交换**，无需直接共享账号/服务器；须先确认可行、合法和确有收益。

**公开仓库提醒**：目前本仓库为 public。GitHub 的 branch、PR、Issue 并非保密空间；Muse 不得把未经授权的经营数据、联系信息、API Key、Cookie 或私人报告放入公开仓库。必要时用户批准后建立私有结果库。

## 4. Muse 独立版的最终业务定义

不是「自动整理网络新闻」，而是面向屈臣氏中国大陆线上零售负责人，持续完成**公开信息发现→真伪/日期/地域/品类审核→多源去重→经营事件→影响机制和可执行建议→长期历史跟踪→周期报告**。

关键主题：美团闪购、京东秒送/京东到家、淘宝闪购、抖音小时达、个护美妆、渠道平台政策与竞对；辅助分析 B2C 旗舰电商与 ToB/经销渠道影响。

保留旧版**每日入池但不发日报、周/月/年报为主、少而精、证据可追溯、事实与推断分离、禁止虚构销售数据和来源**等业务硬要求。旧版 `docs/acceptance_criteria.md` 是重要质量参考，但原 Python 技术手段和付费模型逻辑不是 Muse 必须照抄的运行方案。

## 5. 分阶段工作与可判定结果

| 阶段 | Muse 实际要做的事 | 完成证据 |
|---|---|---|
| S0 能力核验 | GitHub 阅读/获批写入、能打开中国大陆网页、确认持久化与监测能力 | 状态与真实权限记录，未支持不装作支持 |
| S1 首次试跑 | 最近 72 小时自主搜索、核实来源/日期、去重、事件分级、商业影响分析 | 有真实链接和时间的**首次独立情报报告** |
| S2 记忆与报表 | 历史事件账本、来源贡献、周/月/年模板、跨会话查询 | 再次运行不重复同一事件；有可溯源周报草稿 |
| S3 自动化 | 在 Muse 真正支持且用户批准时设置周期任务 | 真实触发记录、失败信息与补救说明 |
| S4 A/B 对照 | 同一事实时间窗比较独特高价值事件、误报、报告质量、维护成本 | 对照表 + 是否值得扩大使用的结论 |

**首个明确可交付结果是 S1 实际试运行报告，绝非只画系统结构图、列待办或生成虚假的新闻案例。** 能自动生成播客/自动发邮件属于功能验证与获得发送授权后的后续阶段。
