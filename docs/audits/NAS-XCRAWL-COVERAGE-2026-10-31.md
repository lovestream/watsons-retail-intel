# XCrawl 故障排查与通道覆盖率量化｜2026-10-31

## 1. 结论先行

**XCrawl 没有"坏"，是慢 + 重试放大。** 它也不是采集源，只做正文补全，所以它故障**不影响采集广度**。

| 项目 | 实测 |
|---|---|
| 单次成功抓取耗时 | **27.6s**（原超时阈值 30s，仅剩 2.4s 余量） |
| 4 日抓取成功率 | 90% / 69% / 69% / 77% |
| 每日超时重试次数 | 59 / 34 / 24 / 19 次 |
| 作为独立采集源占比 | **0%**（4 日 289 篇中 0 篇） |

## 4. 根因分析

1. **超时阈值贴着实际耗时**：服务端稳定在 27-28s，阈值 30s，任何抖动都触发 ReadTimeout。
2. **超时被当成瞬时抖动重试**：`MAX_RETRIES_PER_URL=1`，对"服务端慢"这种确定性失败重试无意义，只会把 8 分钟拖成更久。
3. **单域名慢站拖累整轮**：某个站点持续超时，仍逐条排队等超时。

## 5. 已实施修复

| 改动 | 说明 |
|---|---|
| 超时 30s → **45s** | 覆盖 P95，可 `XCRAWL_SCRAPE_TIMEOUT` 覆盖 |
| 超时**不再重试** | 标记 `_timeout`，直接跳过交 L2/其他通道兜底 |
| **域名熔断** | 同域名连续失败 3 次，本轮跳过该域名剩余 URL |
| 超时计数上报 | 日志输出"超时跳过 N 篇"，不再静默 |

## 7. 降级运行保证（不掩盖故障）

- XCrawl 故障时，管线继续用 RSSHub/CloakBrowser/web_monitor 采集，**广度为 100%**。
- 健康检查中 XCrawl 仍独立报告真实状态（**不强行改绿**）；若 `run.xcrawl.com` 不可达，会如实标记 CRITICAL。
- 正文缺失时，`enrich_cleaned_fulltext` 会尝试 L2（CloakBrowser）补全；L2 失败率同样被记录（10-30 为 2/13）。

## 8. 遗留

1. **CloakBrowser L2 正文增强成功率偏低**（10-28 38%、10-30 15%），是"全文质量"的真实短板，比 XCrawl 更值得关注。
2. XCrawl 单次 27s 属服务端特性，无法从客户端根治，只能靠阈值 + 熔断 + 兜底。
