## 2. 核心论证的成本数据（实测补充）

文档主张"节约来自跨日去重，而非少跑几天"。实测支持该论点：

| 指标 | 实测值（W43，2026-10-19~25） |
|---|---|
| 七日 LLM 抽取文章数 | **119 篇** |
| 七日唯一 URL | **16 个** |
| 若同 URL 只抽取一次可省 | **103 篇（87%）** |
| 跨天重复 URL 的事实 hash 是否变化 | **0 个变化 / 38 个完全一致** |

**关键补充**：38 个跨天重复 URL 的事实 hash **完全一致**，说明"同 URL 只抽一次"在当前数据下**不会丢失后续更新**，方案可安全落地。
（若未来出现"同 URL 内容更新"场景，需按文档的 `content_hash` 变化触发重抽，文档已提及，此处仅补实测佐证。）

## 3. 需要补充的三点（不影响批准，但上线前必须明确）

### 3.1 未量化"L0 每日采集"的存储增长

文档提到 append-only `raw_observations` 与正文快照，但未估算存储。
现状：`data/events` 已 **96MB（约 130 天）**。若 L0 每日保存原文 HTML/正文，按每天 ~30-80 篇估算，
需明确保留期（建议 90 天热存 + 归档），否则一年内会到 GB 级。

### 3.2 "周一单次回溯一周"的可行性论证偏弱

文档已正确指出滚动源无法回溯，但没有给出**各类来源的实际可回溯深度**。
建议阶段 0 直接测量：对每个 RSSHub 路由取 `limit=100` 看能覆盖几天，输出"来源×可回溯天数"矩阵，
作为"哪些源必须每日、哪些可每周"的决策依据。这是整个方案最关键的经验数据。

### 3.3 月报/年报"复用下级封账"的边界条件需写成可执行判定

文档提出 `dependencies_closed` 事件，方向正确。但需明确：
- 月报在月初生成时，若最后一周周报尚未闭合 → 是 hold 还是降级为"截至 X 日"？
- 建议默认 **hold**（与现有 P09 的保守策略一致），并在 manifest 记录 `dependency_state`。

## 4. 与既有系统的衔接风险

| 风险 | 说明 | 建议 |
|---|---|---|
| 覆盖门语义变更 | 从"每天有事件文件"改为"四维覆盖"，会导致历史 `data/events` 与新口径不可比 | 新口径并行记录，不覆盖旧指标 |
| 10-12~18 真实缺口 | 改覆盖算法**不能**把真实缺口算成正常 | 单独标记 `known_gap_dates`，与"零信号有效日"区分 |
| 上游日级精度 24% | 方案未改善此瓶颈（文档已承认） | 保留为独立待办，勿指望频率调整解决 |
| 旧 cron 配置文件 | `config/cron_*.json` 与现网 jobs 未必一致 | 阶段 0 先只读抓取 NAS 真实 jobs 状态（文档已列） |

## 5. 评审结论

**建议：批准进入阶段 0（只读基线收集），不批准任何 Cron／生产代码变更。**

理由：
1. 方案针对的是真实瓶颈（每天重复 LLM 抽取同一批文章），实测 87% 重复率；
2. 保留每日 L0 采集的判断正确——滚动源确实无法回溯；
3. 迁移路径分 5 阶段且每阶段有回退，工程上稳健；
4. 明确区分"少跑六天"与"覆盖不降"，验收标准定得对。

批准前建议补齐 3.1 存储估算、3.2 回溯深度矩阵、3.3 月报 hold 判定。
