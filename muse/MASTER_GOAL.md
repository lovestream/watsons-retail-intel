## 1. 北极星目标与边界

### 1.1 最终要实现的产品

面向负责屈臣氏中国大陆线上零售多渠道经营管理的使用者，建立一个有持续记忆的行业研究系统。长期追踪中国大陆**即时零售 × 个护美妆**的最新变化，主动完成：

**发现 → 搜索 → 核实 → 去噪 → 事件化 → 历史去重 → 综合分析 → 管理层报告 → 周期跟踪 → 改进。**

用户不需要每天亲自投喂链接、反复给你解释业务背景、或者人工复制上次报告；你应尽力利用 Muse 已经正式开放并被当前账号验证的能力持续工作。

产品要解决的不是「报道多少篇新闻」，而是：
- 最近一周/一个月什么变化可能影响屈臣氏的流量、转化、履约成本、货盘、品牌合作和利润？
- 哪些平台、竞对、品类与政策变化值得优先响应？
- 对屈臣氏各渠道有何不同影响？哪些是明确事实，哪些是假设与推演？
- 建议采取什么具体动作、在什么窗口验证、用什么 KPI 追踪？
- 有无能推翻当前判断的反例？上期建议是否出现新证据？

### 1.2 三层渠道经营视角（固定）

1. **即时零售**：美团闪购、京东秒送/京东到家、淘宝闪购、抖音小时达等；
2. **B2C 旗舰电商**：天猫官方旗舰店、京东旗舰店；
3. **ToB/经销**：天猫超市、京东自营、经销商体系。

主监测目标为即时零售 × 个护美妆；分析有证据显示跨渠道影响时，才延伸至 B2C 和 ToB，不能用泛电商资讯稀释重点。

### 1.3 业务主题（重要度动态调整）

重点追踪：平台规则、流量分配、补贴、抽佣、商家激励和入驻；美妆个护商品与品牌供给、类目结构、爆品、场景消费；消费者即时需求、配送/履约、价格与促销；丝芙兰、万宁、调色师、妍丽、话梅等竞对动作；化妆品相关监管政策、营销规则、渠道生态。

严格排除：无即时零售/个护美妆经营交集的泛新闻、资本市场价格/估值/IPO/投研、纯境外主体新闻、无证据的传闻、重复转载、老事件伪装新动态、低价值广告与单一泛关键词碰瓷新闻。香港、澳门、台湾及其他境外主体不进入主报告；涉及其在**中国大陆实际经营**的事例，须以大陆事件主体与明确证据重新判断，默认严审。

### 1.4 现有系统的产品决策必须继承

- **不恢复每日推送日报**。Muse 每天做信息追踪和事实入池；正式面向用户的重点产物为**周报、月报、年报**，可以按需进行临时专题研究。
- 报告内容要求**少而精、事实可靠、讲透经营意义、建议可执行**。没有足够有效事件时明确说明「本期有效新信号不足」，不得硬凑篇数。
- 中文（简体）写作；北京时间 Asia/Shanghai；报告明确完整的覆盖区间。
- 保留原项目对事实、日期、数字、来源链接、内容边界、章节审稿的严格约束；不需要原样照搬全部技术实现。
- 播客与 HTML 邮件是**目标能力**，但首次试运行默认禁发真实邮件、禁用自动外部投递；Muse 账号实际具备对应功能且用户另行批准后才启用。若无法生成合规音频，不能宣称「全功能已实现」。

## 3. 你必须自己建立的七个模块（优先原生 Agent，不盲目编程）

### M1 业务规则与来源知识

将原仓库的目标、边界、渠道群、来源清单、竞对、关键词、重要度、报告要求等浓缩成一份 **Muse 能反复读取并遵守的项目规则**。分清「不可更改的业务硬规则」「可以调整的搜索策略」「原 Python 的实现细节」。建立来源分组：平台/品牌/监管官方、可信商业媒体、美妆和零售垂直媒体、搜索发现类。

输出：`muse/PROJECT_RULES.md`、`muse/SOURCE_STRATEGY.md`；每次改业务边界必须留版本记录。

### M2 自主搜索和事件发现

每天搜索中国大陆即时零售个护美妆的**新经营事实**，按照「平台动作×品牌/品类×竞争对手×商业变量」组合搜索。官方来源优先；行业媒体补充；自主发现新的可信来源。优先搜索过去 24~72 小时，同时维护 7 天回溯窗口处理迟发现，但报告必须按事实发生日归入正确周期。

只抓你可合法访问的公开信息，遵守网站协议与访问限制；无法访问的页面标记“无法核验”，不要编造正文或绕过验证码、登录限制。

来源记录至少包括：URL、标题、媒体/官方主体、发布时间、事件发生时间、实际发现时间、所涉及平台/品牌/品类及简短证据摘录。时间未知的候选不直接进正式池。

输出：当天搜到什么、遗漏哪些关键平台、哪些网站打不开、哪些是可验证事实；不要只有一篇泛泛的摘要。

### M3 事实提取、质量控制、历史去重

把新闻文章转为**具体事实事件**，而不是让「每篇文章 = 一条新闻」。同一个平台政策被 6 家媒体报道应合并为一件事；同一政策过了两周出现真实新变化，允许记录事件更新，不得误杀。

每件事至少拥有：
`event_id`（稳定标识）、`fact`（中性事实）、`event_date`、`published_date`、`first_seen`、`region`、`topic`、`channels`、`subjects`、`primary_url`、`supporting_urls`、`evidence`、`source_type`、`verified`、`priority`、`status`、`update_of`（如为后续进展）、`last_updated`。

不得因有两条来源就认为事实必然真实：核实来源是否独立、是否互相转载、是否为单方广告主张。无法确认的数值或主体写「未核实」，不写推测的增长率/市占率/GMV。

重要度参考原 `config/scoring.yaml` 的八维结构（战略重要性、屈臣氏相关度、影响范围、来源可信度、数据、行动性、时间敏感度、新颖性）；Muse 可以用简单的 P0/P1/P2/ARCHIVE 分级，而非必须复刻每个公式。无法核实出处、与业务无关、无具体事实者不能升为 P0/P1。

输出：持久化事件登记表、去重规则、更新记录、来源证据，至少能防止下一次会话重复记同一新闻。

### M4 经营影响分析：核心价值所在

每个 P0/P1 信号必须回答：

**事实是什么 → 变化的机制是什么 → 对屈臣氏哪一类渠道/业务变量有影响 → 建议什么动作 → 用什么数据和期限验证 → 哪些条件会推翻判断**。

明确区分：
- **已证实事实**（有 URL 与日期）；
- **商业机制推断**（需要解释逻辑、边界和替代解释）；
- **建议动作**（探索性行动，不是假装企业已经执行）；
- **内部验证依赖**（需要屈臣氏真实销售、毛利、库存、流量等数据时只能列待验证项，不能编造）。

重点业务变量：客流/流量、转化率、客单、复购、毛利、扣点与投放、补贴、货盘 SKU、库存、履约时效、会员、品牌谈判与渠道关系。必须具体到适用渠道及验证指标，避免「继续关注、加强合作、优化体验」等空话。

### M5 周报、月报、年报和专题研究

首要交付是**可独立阅读、可点击原始证据、经营观点鲜明**的中文管理层报告：
- 周报：6 章，覆盖本周核心判断、主要趋势、平台变化、竞对变化、品类与渠道影响、下周优先动作；
- 月报：7 章，覆盖关键判断、平台结构变化、品类演变、竞对行为、经营启示、下月动作、风险机会；
- 年报：8 章，覆盖全年关键判断、阶段回顾、品类、平台、竞争格局、年度启示、下一年动作、长期风险；
- 专题：根据用户临时的问题深挖一个平台/品类/竞对；专题不是日报，需清晰写研究时间范围。

**不降低原仓库的内容硬门槛**：
- 必需章节完整，周/月/年分别 6/7/8 章；本期来源覆盖不足要显著披露；
- 当期事件必须在有效统计区间；若引用背景信息需标记“背景”；
- 不在正式报告混入内部 event_id、调试标签、模型思考内容；
- 不伪造数字、政策文本、市场份额、内部数据；
- 优先展示 3~5 个重要经营判断，每个判断配可点击证据与可执行动作；
- 结论不能仅因报道频繁就断言趋势或因果；
- 每期最后留下“下周期待验证的假设与指标”，下期回看。

输出应适合经理在 5~10 分钟阅读（深度附录可另附）；旧系统要求的字数/播客时长可作为目标而非强行凑量。未能通过事实审校时产出**标明不可发布的草稿**，不自动发送。

### M6 长期记忆、复盘和迭代

建立可查询的项目历史：规则版本、来源有效性、事件及更新、周/月报告、上期未验证假设、本期完成情况、错误原因。每次运行只读取相关摘要与近期账本，避免重复全量读取大量历史文章。

持续改进：哪些关键词带来噪音？哪些来源真正贡献独特 P0/P1 事件？上次误判是什么？哪些结论缺乏证据？历史结果可用于调整**搜索与分析策略**，但不能自动突破业务边界与权限。

输出：`muse/OPERATIONS.md`、简短的变更记录和定期质量复盘。

### M7 背景运行、成果保存与交付（先测试，再启用）

如果当前 Muse 账号确实支持重复监控/定期任务：
- 默认目标：**每天**形成事件池；**每周一**完成上一自然周周报；**每月 1 日**完成上月月报；**每年 1 月 1 日**完成上年年报；日期、统计区间与任务解释全部以**北京时间**为准。
- 尽量设置每日北京时间 07:30 之后搜集最近闭合窗口 `昨天 07:00 ~ 今天 07:00`；周/月/年在数据准备完成后生成。实际调度精度、时区支持和漏跑补救以产品功能核实，不可假设一个网页端定时任务等于 OS cron。
- 如果平台只支持一次性「监测提醒」或后台任务、无法精准重复运行：应设置**可真实验证**的最接近方案，明确功能差距；不要宣称持续自动化已建成。
- 每次完成一项任务必须留下日期、结果、引用与状态。**任务安排成功 ≠ 任务执行成功**。
- 输出状态至少：`planned`、`running`、`succeeded`、`degraded`、`failed`、`needs_approval`。如平台不提供运行日志，保存最小化完成证明与任务结果索引。
- Muse 如果能够给用户发送提醒，可先只做**完成通知/失败告警**；未经用户另行授权，不向现有收件人自动发送周/月/年邮件，也不自动发播客。
- 若有官方 TTS、文件导出或邮箱连接器，在能力核实且用户批准后单独开通；不把这一阶段的缺口包装成已实现。

## 6. 质量指标和退出条件
