## 2. 单次运行流程（手动/自动同构）

1. 读 `PROJECT_RULES.md` 与最近 30 天账本（去重基线）。
2. 按查询矩阵执行搜索，记录每组 query、命中数、时间窗。
3. 打开候选原文核验（时间、事实、数字口径）；无法核验的单列清单。
4. 事件化：合并同源报道、识别进展更新、剔除硬排除项，并为每个淘汰给出至少一个示例理由（试运行/复盘时）。
5. 分级 P0/P1/P2/ARCHIVE；对 P0/P1 写完整经营分析（DATA_SCHEMA §4 结构）。
6. 写入账本；运行记录写入 `muse/runs/RUNLOG.md`（日期、窗口、检查来源数、候选/核实/采纳/待核实数、失败清单、状态）。
7. 到报告周期则按 DATA_SCHEMA §5 生成报告并自审（章节数、证据链接、数字口径、无内部标记、覆盖率披露）。

## 3. 运行状态

`planned` / `running` / `succeeded` / `degraded`（部分来源失败但完成）/ `failed` / `needs_approval`。
任务被安排 ≠ 任务执行成功；每次运行以 RUNLOG 记录为准。

## 4. 失败与恢复

- 搜索不可用/来源大面积打不开：状态记 degraded/failed，列明失败来源与替代来源；不得用记忆中的旧闻冒充当期结果。
- 中断恢复：新会话先读 `muse/README.md` 状态区 + 最近账本 + RUNLOG，即可续跑；账本 event_id 不复用。
- GitHub 同步失败：成果先留 Muse 工作区，恢复后补同步，并在 CHANGELOG 注明。

## 5. 权限与告警

- P0 信号、运行失败、覆盖率跌破 minimum：主动提示用户。
- 正式邮件发送、播客生成、付费服务：未获用户单独授权前不启用（见 MASTER_GOAL §1.4）。
- GitHub 写入仅限 `muse/` 目录，走官方连接器与审批。

## 6. 复盘（每月至少一次）

- 关键词噪音：哪些 query 只带来噪音，拟删/改；
- 来源贡献：各 Tier 来源贡献的 P0/P1 数，零贡献来源处理；
- 误判回收：上期判断被新证据推翻的，记录原因并更新账本 status；
- 覆盖缺口：哪些平台/品类长期零覆盖及补搜策略。
复盘结论写入本文件修订或 CHANGELOG；不得突破 PROJECT_RULES 硬边界。
