## S1 验收用例（首次试运行）

- [x] 观察窗口明确：最近 72 小时（起止时间标注，北京时间）
- [x] 至少覆盖平台动态、个护美妆品类、重要竞对三个维度，并记录每维度候选/采纳数（实测四维度，含监管）
- [x] 每条采纳事件：URL + 发表时间 + 发生时间 + 事实 + 证据摘录齐全，可人工逐条打开复核
- [x] 完成地域/相关性/真实性/时效/跨源去重；至少展示 1 例淘汰及理由（报告列 6 例）
- [x] 最高价值信号有完整的「事实→机制→影响→动作与 KPI→反证」分析
- [x] 报告显著标注「72 小时试运行，非完整周报」；不外发邮件
- [x] 运行数据（检查来源数、候选、核实、采纳、待核实、失败清单）写入 RUNLOG

## S2 验收用例（记忆与模板）

- [ ] 新会话依据账本识别 ≥3 条旧事件且不重复记为新事件
- [ ] 生成一期标注「覆盖不足」的演示周报（6 章齐全），不冒充正式达标周报

## S3 验收用例（自动化）

- [ ] 定时任务真实创建并有 ≥2 次实际运行记录（RUNLOG 可查）
- [ ] 漏跑/失败有提示；不重复汇报同一事件

## 已知缺口与替代方案

| 缺口 | 替代方案 |
|---|---|
| GitHub 同步依赖连接器（git 直推不可用） | 日常同步走连接器快照推送至独立分支 + PR，并回读验证；同步记录存工作区外 JSON |
| 部分大陆站点可能无法直接打开 | 用搜索结果的来源时间与多源交叉核验；无法核验者降级/淘汰并记录，不编造 |
| 网页端调度精度不等于 OS cron | 以平台 cron 实测运行记录为准；漏跑时手动补跑并在 RUNLOG 注明 |
